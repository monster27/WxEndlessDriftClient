# 📁 Addressables 自动化工具开发与深度排坑全记录

> 本文档记录了 `AAutoPackTool` 从 0 到 1 的完整开发、踩坑、重构与最终稳定版的全过程。
> 适合作为团队架构分享、技术交接文档、或后来者的避坑指南。

---

## 📝 一、 前言与目标

**目标**：开发一个编辑器工具（`AAutoPackTool`），实现：

- 一键重置底层 AA 环境
- 按文件夹及包体真实大小智能分组（图集与普通资源分开处理）
- 批量移入资源并打标（**不卡死、不 `Hold on`**）
- 快捷打资源（带时间戳目录，防版本覆盖）
- 一键打开微信小游戏转换界面（不越权自动 DoExport）
- 分析已打出来的 bundle，一眼看出哪些包过大/过小

**核心挑战**：

1. 彻底解决批量 `CreateOrMoveEntry` 导致的 `Hold on (busy for XXXs)` 假死和底层 `NullReferenceException`。
2. 解决图集（`.spriteatlas`）体积失真导致的**巨包**（25.6MB）和**碎包**（12KB/36KB）并存问题。
3. 找到微信小游戏的**甜区阈值**，在「请求数少」和「流量省」之间取得平衡。

## 🕳️ 二、 排坑过程（共 12 个坑）

### 坑 1：纯同步 For 循环（最初的灾难）

- **做法**：`foreach` 把几百个资源通过 `CreateOrMoveEntry` 塞入组中。
- **现象**：瞬间假死，弹 `Hold on`，一卡就是几十秒甚至几小时。
- **原因**：`CreateOrMoveEntry` 底层**同步阻塞**。每次移组都会触发：依赖树重算 → 计算 Hash → 序列化写盘 → 刷新 UI。连续执行累加了这几百次操作的耗时，直接撑爆单帧时间。

### 坑 2：`StartAssetEditing` 批量挂起（导致死锁）

- **做法**：`AssetDatabase.StartAssetEditing()` 包裹整个 For 循环，企图阻止每次移组引发的刷新。
- **现象**：依然卡死，甚至引发更严重的底层死锁。
- **原因**：虽然挂起了 UI，但 Addressables 移组极度依赖实时的 Asset 读取。挂起状态下拿不到最新依赖，直接内部死锁。

### 坑 3：时间片限制（伪异步）

- **做法**：`Stopwatch` 限制每帧最多执行 20ms 就跳出，企图分帧处理。
- **现象**：毫无作用，依然卡死。
- **原因**：`CreateOrMoveEntry` 是**原子操作**。单次移入一个包含百张图的图集，单次执行可能就耗时 2 秒。你无法在 20ms 处中断它，它依然会把这一帧撑爆。

### 坑 4：官方 API 建组报空引用

- **做法**：官方的 `settings.CreateGroup` 创建分组。
- **现象**：抛出 `Object reference not set to an instance of an object`，但诡异的是组却成功建出来了。
- **原因**：Unity 2022 版本中，如果底层 `AssetGroupTemplates` 文件夹或 Profile 变量丢失，官方 `CreateGroup` 在挂载 Schema 时必定报空。

### 坑 5：`Addressable content build failure (duration: 0:00:00)`

- **现象**：打资源时瞬间秒崩，报错指向 `BuildPlayerContent` 空引用。
- **原因**：
  1. 底层自愈代码用力过猛，给系统专属的 `Built In Data` 组强行塞入了 `BundledAssetGroupSchema`，导致底层规则冲突。
  2. 本地的 Profile 变量 `Remote.BuildPath` 没有被正确赋值，打包时读取到空路径引发崩溃。
  3. 内存中残留了同名但被销毁的 Group 引用，或者列表中存在同名组导致遍历崩溃。

### 坑 6：远程 URL 里 `[BuildTarget]` 与手写 `WebGL` 重复

- **现象**：运行时所有 bundle 请求 `404 Not Found`，日志里 URL 是 `https://xxx.top/aa/WebGL/WebGL/group_xxx.bundle`。
- **原因**：配置文件里 `remoteLoadPath = "https://xxx.top/aa/WebGL/[BuildTarget]"`。`[BuildTarget]` 是 Addressables 内置变量，在 WebGL 平台会被自动替换成 `WebGL`，最终拼成 `WebGL/WebGL`。
- **修复**：把 `remoteLoadPath` 改为 `https://xxx.top/aa/WebGL`（去掉 `[BuildTarget]`），路径里不再手写和变量双重叠加。

### 坑 7：图集被当作几 KB 的小 unit 参与普通装箱

- **现象**：某次打出来的 `Group_13` 分析显示 0.28 MB，实际 bundle 25.6 MB。其他组又特别小（12KB、36KB 碎包）。
- **原因**：
  - 装箱算法按 `new FileInfo(file).Length` 统计体积，`.spriteatlas` 本身只有几 KB，但打包时会把它引用的所有纹理（总计几十 MB）全拉进同一个 bundle。
  - 于是图集被当成「几 KB 的小 unit」，被 best-fit 塞进容量最充裕的普通组，打包后该组瞬间膨胀。
- **分析结论**：**图集必须用真实纹理依赖体积估算，不能只看 `.spriteatlas` 文件本身。**

### 坑 8：矫枉过正——每个 `.spriteatlas` 独立成组

- **做法**：发现坑 7 后，第一个修复方案是「每个 `.spriteatlas` 强制独立成 `Group_Atlas_XXX`」，并给每个图集用 `AssetDatabase.GetDependencies` 真实估算体积。
- **现象**：直接打出了 **104 个 bundle**。图集一多，组数就按图集文件数量膨胀，光请求握手就要爆。
- **原因**：图集组数 = 图集文件数，而不是按体积合并。**这是从「塞进普通组」矫枉过正到「完全隔离」的典型错误。**
- **正确做法**：图集仍然按体积装箱，但**只和图集合并，不和普通资源混**，组数 ≈ `ceil(总图集体积 / idealMax)`，个位数到十几个，而不是等于文件数。

### 坑 9：装箱算法 `CurrentSize < minBytes` 判断反效果

- **代码**（有问题的版本）：
  ```csharp
  if (minCapacityGroup != null && minCapacityGroup.CurrentSize < minBytes)
  {
      minCapacityGroup.AddUnit(unit);
      continue;
  }
  // 否则创建新组
  ```
- **含义**：只有当组当前大小 `< 512KB` 时才往里塞。
- **现象**：组一旦达到 512KB 就停止接收，下一个单元只能新建组；新组从 0 开始又容易被塞到 512KB 就停，反复产生**半满组**和 **12KB / 36KB 碎包**。
- **正确做法**：改用**标准 best-fit**——优先塞进「最满且装得下」的组，把空隙填满；只有真的装不下才建新组。

### 坑 10：category 按「目录/文件名」返回，永远无法合并

- **代码**（有问题的版本）：
  ```csharp
  var parts = path.Split('/');
  if (parts.Length >= 5) return parts[3] + "/" + parts[4];
  ```
- **对于 `Assets/Addressables/UI/Textures/foo.png`**：`parts[3] = Textures`，`parts[4] = foo.png`，返回 `Textures/foo.png`——**每个文件一个 category**。
- **后果**：`sameCategoryGroup` 永远为 null，所有资源都走全局 best-fit，分组极不稳定，同类资源被打散。
- **正确做法**：返回目录（如 `UI/Textures`），同目录资源优先聚在一起。

### 坑 11：View 独立拆包（曾经的"最佳实践"，后来被数据推翻）

- **初衷**：`UI/View/*.prefab` 独立成 `Group_View_XXX`，让打开某个界面时只下载对应包。
- **实测数据**：13 个 View 组，体积 **6.7 KB ~ 70.5 KB**，合计约 350 KB。
- **问题**：
  - 微信小游戏 `wx.request` 最大并发约 **10**，13 个 View 触发并发限制，超出的排队。
  - 一次 HTTP 请求头部约 1~2 KB，TLS 握手 1~2 RTT。**下载 6.7 KB 的时间，握手占了大头**。
  - 合并成 1 个 350 KB 包，一次请求完成，**比 13 次请求快得多**。
- **重要澄清**：合并 ≠ 全部加载。Addressables 的 `AssetLoadMode = Requested Asset And Dependencies`（默认）**只会把被请求的 Prefab 及其依赖加载到内存**，同 bundle 里其他 Prefab 只是"躺在下载好的文件里"，不占内存。
- **最终决定**：删除 `viewPerPrefab` 功能，View prefab 与普通资源一视同仁，按目录 category 合并。

### 坑 12：打包小程序功能「过度自动化」

- **早期做法**：反射读取 `MiniGameConfig.asset` 里的 `DST` / `webglDir` / `ProjectConf` 字段，自动改路径、自动调 `DoExport`、自动生成时间戳导出目录。
- **现象**：
  - 不同版本 WX-WASM-SDK-V2 字段结构不同，反射字段名对不上就报错。
  - 自动 DoExport 可能打包到意想不到的目录，需要一套备份/恢复逻辑。
  - 用户实际只想「打开微信转换界面」，剩下的自己点。
- **最终决定**：删掉所有反射改配置、自动 DoExport、时间戳导出目录的逻辑。**只做一件事**：
  ```csharp
  EditorApplication.ExecuteMenuItem("微信小游戏/转换小游戏");
  ```
  失败时退化为打开 `WXEditorWindow` 窗口，再失败就弹提示让用户手动点。

## 🛠️ 三、 终极解决方案

### 1. 建组：反射物理建组，绕过官方 `CreateGroup` 雷区

- **为什么**：Unity 2022 官方 `CreateGroup` 有底层模板空引用 Bug（坑 4）。
- **实现逻辑**：
  - `ScriptableObject.CreateInstance<AddressableAssetGroup>()` 在内存建组。
  - 反射设置底层真实组名 `m_GroupName`。
  - `ScriptableObject.CreateInstance` 创建 Schema（`BundledAssetGroupSchema`、`ContentUpdateGroupSchema`），存入硬盘。
  - 反射（`m_Group` 字段）把 Schema 与 Group 互相关联。
  - `AssetDatabase.CreateAsset` 把 Group 写入硬盘。
  - 反射（`m_GroupAssets` 字段）把 Group 塞入 Settings 列表，调用 `RemoveAll` 清洗可能存在的同名残留，**彻底解决 UI 显示双份组**。

### 2. 移组：单帧单次的极速异步队列

- **为什么**：`CreateOrMoveEntry` 是原子阻塞操作（坑 1、坑 3），必须让出主线程。
- **实现逻辑**：
  - 提前算好所有文件的归属，生成 `Queue<(string file, AddressableAssetGroup group)>`。
  - 注册 `EditorApplication.update`。
  - 每次 Update 只 `Dequeue` 一个任务，执行完立刻 `Repaint` 刷新进度条并结束当前帧。
  - 单次操作最多卡顿 30ms，绝不触发 `Hold on`。实测总耗时反而变短，因为让出主线程后 Unity 底层调度更顺畅。

### 3. 打标与地址：纯 IO 遍历 + 强制覆盖

- **为什么**：打标记不涉及复杂图集移组，但仍要防止大量文件阻塞。
- **实现逻辑**：`Directory.GetFiles` 纯 IO 扫描，`entry.SetAddress(assetPath, false)` **强制覆盖旧地址**，防止历史脏数据导致运行时找不到资源。

### 4. 图集体积：真实纹理依赖估算，不是 `.spriteatlas` 文件大小

- **为什么**：`.spriteatlas` 只有几 KB，但打包后 bundle 包含几十 MB 纹理（坑 7）。
- **实现逻辑**：
  ```csharp
  long GetAtlasRealSize(string atlasAssetPath)
  {
      long total = 0;
      var visited = new HashSet<string>();

      if (File.Exists(atlasAssetPath))
      {
          total += new FileInfo(atlasAssetPath).Length;
          visited.Add(atlasAssetPath);
      }

      var deps = AssetDatabase.GetDependencies(atlasAssetPath, true);
      foreach (var dep in deps)
      {
          string d = dep.Replace('\\', '/');
          if (visited.Contains(d)) continue;
          if (!d.StartsWith("Assets/")) continue;
          if (d.EndsWith(".cs") || d.EndsWith(".meta") || d.EndsWith(".asmdef")) continue;
          if (!File.Exists(d)) continue;
          total += new FileInfo(d).Length;
          visited.Add(d);
      }
      return total;
  }
  ```

### 5. 图集与纹理不重复：扫描图集引用，跳过纹理 entry

- **为什么**：如果纹理既被图集引用，又被单独标记成 Addressable entry，就会同时进入图集 bundle 和普通 bundle，**体积翻倍**。
- **实现逻辑**：
  - 先扫描所有 `.spriteatlas`，收集它们引用的纹理路径放入 `atlasTextures`。
  - 构建单元时，`atlasTextures.Contains(path)` 的纹理**直接跳过**。
  - 图集 bundle 天然包含 `.spriteatlas` + 它引用的纹理，不会重复。
  - 唯一还会重复的情况：某个 prefab **直接引用** `Assets/Textures/xxx.png` 的 Texture2D（而不是通过图集里的 sprite）。这是 prefab 层面的事，代码无法自动修。

### 6. 图集与普通资源：分开装箱，各自独立阈值

- **为什么**：图集 LZ4 压缩比约 3x，普通资源约 1.3x（prefab/json 压缩率低）。用同一套阈值会一方偏紧一方偏松。
- **实现逻辑**：`AAutoPackConfig` 里维护两套阈值。

  | 配置项 | 值 | 说明 |
  |---|---|---|
  | `minBundleKB` | 512 | 普通资源最小装箱单元 |
  | `idealMaxKB` | 2048 | 普通资源理想上限（打包后约 1.54 MB） |
  | `hardMaxKB` | 4096 | 普通资源硬上限 |
  | `atlasIdealMaxKB` | 6144 | 图集理想上限（未压缩，打包后约 2 MB） |
  | `atlasHardMaxKB` | 12288 | 图集硬上限（未压缩，打包后约 4 MB） |

- 装箱时：
  ```csharp
  bool isAtlasUnit = IsAtlasPath(unit.Key) && unit.Key.EndsWith(".spriteatlas");
  long currentIdealMax = isAtlasUnit ? atlasIdealMaxBytes : idealMaxBytes;
  long currentHardMax  = isAtlasUnit ? atlasHardMaxBytes : hardMaxBytes;
  ```

### 7. 装箱算法：best-fit + 兜底合并

- **为什么**：坑 9 的 `CurrentSize < minBytes` 判断反效果，坑 10 的 category 按文件名导致永远无法合并。
- **category 修复**：
  ```csharp
  private static string GetParentCategoryStatic(string path)
  {
      string normalized = path.Replace('\\', '/');

      // 图集：ATLAS/<目录>，同目录图集可合并
      if (normalized.EndsWith(".spriteatlas") && normalized.Contains("/Atlases/"))
      {
          var dir = Path.GetDirectoryName(normalized).Replace('\\', '/');
          if (dir.StartsWith("Assets/Addressables/"))
              dir = dir.Substring("Assets/Addressables/".Length);
          return "ATLAS/" + dir;
      }

      // 普通资源：按目录（不是"目录/文件名"！）
      var normalDir = Path.GetDirectoryName(normalized).Replace('\\', '/');
      if (normalDir.StartsWith("Assets/Addressables/"))
          normalDir = normalDir.Substring("Assets/Addressables/".Length);
      return normalDir;
  }
  ```
- **best-fit**：
  ```csharp
  // 1. 优先塞进同 category 且装得下的最满组
  var sameCategoryGroup = groups
      .Where(g => g.Category == category
          && (g.CurrentSize + unit.Value) <= currentIdealMax
          && (isAtlasUnit ? g.GroupName.StartsWith("Group_Atlas_") : !g.GroupName.StartsWith("Group_Atlas_")))
      .OrderByDescending(g => g.CurrentSize)
      .FirstOrDefault();
  if (sameCategoryGroup != null) { sameCategoryGroup.AddUnit(unit); continue; }

  // 2. 再找任意装得下的最满同类型组（图集只合并图集，普通只合并普通）
  var bestFitGroup = groups
      .Where(g => (g.CurrentSize + unit.Value) <= currentIdealMax
          && (isAtlasUnit ? g.GroupName.StartsWith("Group_Atlas_") : !g.GroupName.StartsWith("Group_Atlas_")))
      .OrderByDescending(g => g.CurrentSize)
      .FirstOrDefault();
  if (bestFitGroup != null) { bestFitGroup.AddUnit(unit); continue; }

  // 3. 装不下才创建新组
  ```
- **兜底合并**（消灭孤包）：
  ```csharp
  private int MergeSmallGroups(List<GroupPlan> groups, long minBytes, long idealMaxBytes, long atlasIdealMaxBytes)
  {
      int mergedCount = 0;
      bool merged = true;
      int guard = 0;

      while (merged && guard++ < 1000)
      {
          merged = false;
          var smallGroups = groups.Where(g => g.CurrentSize < minBytes).ToList();
          if (smallGroups.Count == 0) break;

          foreach (var small in smallGroups)
          {
              bool smallIsAtlas = small.GroupName.StartsWith("Group_Atlas_");
              long limit = smallIsAtlas ? atlasIdealMaxBytes : idealMaxBytes;

              var target = groups
                  .Where(g => g != small
                      && g.GroupName.StartsWith("Group_Atlas_") == smallIsAtlas
                      && (g.CurrentSize + small.CurrentSize) <= limit)
                  .OrderByDescending(g => g.CurrentSize)
                  .FirstOrDefault();

              if (target != null)
              {
                  foreach (var unit in small.Units) target.AddUnit(unit);
                  groups.Remove(small);
                  merged = true;
                  mergedCount++;
                  Debug.Log($"[AA] 兜底合并：{small.GroupName} ({small.CurrentSize / 1024f:F1}KB) -> {target.GroupName} (新大小 {target.CurrentSize / 1024f:F1}KB)");
                  break;
              }
          }
      }
      return mergedCount;
  }
  ```

### 8. 甜区阈值：请求少 + 流量省

**为什么是 0.5 ~ 2 MB（打包后）**：

- 微信官方建议单 AssetBundle 包体 **≤ 2 MB**。
- 微信底层 `wx.request` 最大并发约 **10 个**，包少才能避免并发排队。
- 单包 2 MB 弱网下约 1~2 秒，体验可接受。
- LZ4 压缩比：图集约 **3x**，普通资源约 **1.3x**。

**装箱阈值（≈未压缩）→ 打包后估算**：

| 类型 | 装箱 min | 装箱 ideal | 打包后健康范围（估算） |
|------|---------|-----------|---------------------|
| 普通资源 | 512 KB | 2048 KB | 0.38 ~ 1.54 MB |
| 图集 | — | 6144 KB | ~2.00 MB |
| 允许超出 | — | — | 15% 以内不警告 |

**图集硬上限**：`atlasHardMaxKB = 12288`（未压缩 12 MB ≈ 打包后 4 MB）。超过就单独成组，但一般不会触发。

### 9. 分析工具：让"哪些包有问题"一眼可见

- **`📊 分析打出来的资源`** 按钮，自动识别最新时间戳目录，逐个 bundle 打印体积。
- **分类标注**：
  - `[内置/场景组]`：`group_0_assets_all`（Built In Data）、`group_*_scenes_all`（Default Local Group 场景）。**工具管不到，需要手动改 `Bundle Mode`。**
  - `[Atlas]`：图集组，用独立阈值判断过大。
  - 无标注：普通资源组。
- **判断规则**：
  - 过小：`size < minBundleKB × 1024 / 1.3`（打包后）。
  - 过大：普通 > `idealMaxKB × 1.15`；图集 > `atlasHardMaxKB × 1024 / 3 × 1.15`。
  - 允许超出 15%，避免估算误差导致的无谓警告。
- **输出统计**：总包数、总体积、过小/正常/过大数量、图集/普通/内置分类统计。

### 10. 内置组必须手动处理

- `group_0_assets_all` = **Built In Data**（引擎管理，新版本 Addressables 可能没有 `Bundle Mode` 选项）。
- `group_*_scenes_all` = **Default Local Group 的场景**（4 MB 左右，工具改不了）。
- **手动操作**：`Window > Asset Management > Addressables > Groups` → 点 `Default Local Group` → 右侧 `Content Packing & Loading` → `Bundle Mode` 改成 `Pack Separately`。改一次永久生效。

### 11. 打包小程序：只打开转换界面

- **不**反射改 `MiniGameConfig` 的 `DST` / `webglDir`。
- **不**自动调 `DoExport`。
- **不**自动生成时间戳导出目录。
- **只做一件事**：
  ```csharp
  private void DoBuildMiniGame()
  {
      const string menuPath = "微信小游戏/转换小游戏";

      try
      {
          if (EditorApplication.ExecuteMenuItem(menuPath))
          {
              UnityEngine.Debug.Log($"[AA] ✅ 已打开微信转换菜单: {menuPath}");
              return;
          }
      }
      catch (Exception e)
      {
          UnityEngine.Debug.LogWarning($"[AA] 执行菜单 {menuPath} 异常: {e.Message}");
      }

      // 退化为打开 WXEditorWindow 窗口
      var wxEditorWindowType = Type.GetType("WeChatWASM.WXEditorWindow, WX-WASM-SDK-V2.Editor")
  ```

## 🛡️ 四、 核心 API 与架构总结（防坑指南）

1. **绝不使用大批量的同步 `foreach`** 进行任何 AA 操作。
2. **移组操作必须使用「单帧单次」的异步队列**。绝不能在循环中同步移组。
3. **建组操作使用反射物理建组**，并在加入 `m_GroupAssets` 前做严格的 `RemoveAll` 防重。
4. **系统组（`Built In Data`、`Default Local Group`）绝不能加入 `BundledAssetGroupSchema`**，只能在自建的组上加。**也不要尝试用工具改它们的打包模式**，去 Groups 窗口手动改。
5. **打包前必须自愈**：强制校验 `Remote.BuildPath` 路径变量非空，`AddressableAssetSettings.CleanPlayerContent()` 清缓存。
6. **图集体积必须用 `AssetDatabase.GetDependencies` 真实估算**，不能看 `.spriteatlas` 文件大小。
7. **图集引用的纹理要跳过，不作为独立 entry**，避免图集 bundle 和普通 bundle 重复打包。
8. **图集和普通资源用各自独立的阈值体系**（图集压缩比约 3x，普通约 1.3x）。
9. **装箱用 best-fit + 兜底合并**，杜绝碎包。绝不用 `CurrentSize < minBytes` 这种判断。
10. **category 必须按目录，不是「目录/文件名」**，否则同类资源永远无法合并。
11. **View 独立拆包不是万能的**：13 个小 View（< 100 KB）合并成一个包更优。只有当 View 数量很多（> 50）或单个很大（> 500 KB）时才值得独立。
12. **不要为了「自动化」而自动化打包小程序**：调起微信转换菜单、让用户自己点，更稳定。
13. **远程路径里不要双重写平台名**：手写 `WebGL` 又要 `[BuildTarget]`，会导致 `WebGL/WebGL`。

## 📝 一、 前言与目标

**目标**：开发一个编辑器工具（`AAutoPackTool`），实现：

- 一键重置底层 AA 环境
- 按文件夹及包体真实大小智能分组（图集与普通资源分开处理）
- 批量移入资源并打标（**不卡死、不 `Hold on`**）
- 快捷打资源（带时间戳目录，防版本覆盖）
- 一键打开微信小游戏转换界面（不越权自动 DoExport）
- 分析已打出来的 bundle，一眼看出哪些包过大/过小

**核心挑战**：

1. 彻底解决批量 `CreateOrMoveEntry` 导致的 `Hold on (busy for XXXs)` 假死和底层 `NullReferenceException`。
2. 解决图集（`.spriteatlas`）体积失真导致的**巨包**（25.6MB）和**碎包**（12KB/36KB）并存问题。
3. 找到微信小游戏的**甜区阈值**，在「请求数少」和「流量省」之间取得平衡。
4. **运行时**：处理 AA 标签无效、资源引用丢失、持久化父级冲突等运行时问题（后文第 13~18 坑）。

## 🕳️ 二、 排坑过程

### 🧱 A. 编辑器打包阶段（坑 1 ~ 坑 12）

#### 坑 1：纯同步 For 循环（最初的灾难）

- **做法**：`foreach` 把几百个资源通过 `CreateOrMoveEntry` 塞入组中。
- **现象**：瞬间假死，弹 `Hold on`，一卡就是几十秒甚至几小时。
- **原因**：`CreateOrMoveEntry` 底层**同步阻塞**。每次移组都会触发：依赖树重算 → 计算 Hash → 序列化写盘 → 刷新 UI。连续执行累加了这几百次操作的耗时，直接撑爆单帧时间。

#### 坑 2：`StartAssetEditing` 批量挂起（导致死锁）

- **做法**：`AssetDatabase.StartAssetEditing()` 包裹整个 For 循环，企图阻止每次移组引发的刷新。
- **现象**：依然卡死，甚至引发更严重的底层死锁。
- **原因**：虽然挂起了 UI，但 Addressables 移组极度依赖实时的 Asset 读取。挂起状态下拿不到最新依赖，直接内部死锁。

#### 坑 3：时间片限制（伪异步）

- **做法**：`Stopwatch` 限制每帧最多执行 20ms 就跳出，企图分帧处理。
- **现象**：毫无作用，依然卡死。
- **原因**：`CreateOrMoveEntry` 是**原子操作**。单次移入一个包含百张图的图集，单次执行可能就耗时 2 秒。你无法在 20ms 处中断它，它依然会把这一帧撑爆。

#### 坑 4：官方 API 建组报空引用

- **做法**：官方的 `settings.CreateGroup` 创建分组。
- **现象**：抛出 `Object reference not set to an instance of an object`，但诡异的是组却成功建出来了。
- **原因**：Unity 2022 版本中，如果底层 `AssetGroupTemplates` 文件夹或 Profile 变量丢失，官方 `CreateGroup` 在挂载 Schema 时必定报空。

#### 坑 5：`Addressable content build failure (duration: 0:00:00)`

- **现象**：打资源时瞬间秒崩，报错指向 `BuildPlayerContent` 空引用。
- **原因**：
  1. 底层自愈代码用力过猛，给系统专属的 `Built In Data` 组强行塞入了 `BundledAssetGroupSchema`，导致底层规则冲突。
  2. 本地的 Profile 变量 `Remote.BuildPath` 没有被正确赋值，打包时读取到空路径引发崩溃。
  3. 内存中残留了同名但被销毁的 Group 引用，或者列表中存在同名组导致遍历崩溃。

#### 坑 6：远程 URL 里 `[BuildTarget]` 与手写 `WebGL` 重复

- **现象**：运行时所有 bundle 请求 `404 Not Found`，日志里 URL 是 `https://xxx.top/aa/WebGL/WebGL/group_xxx.bundle`。
- **原因**：配置文件里 `remoteLoadPath = "https://xxx.top/aa/WebGL/[BuildTarget]"`。`[BuildTarget]` 是 Addressables 内置变量，在 WebGL 平台会被自动替换成 `WebGL`，最终拼成 `WebGL/WebGL`。
- **修复**：把 `remoteLoadPath` 改为 `https://xxx.top/aa/WebGL`（去掉 `[BuildTarget]`），路径里不再手写和变量双重叠加。

#### 坑 7：图集被当作几 KB 的小 unit 参与普通装箱

- **现象**：某次打出来的 `Group_13` 分析显示 0.28 MB，实际 bundle 25.6 MB。其他组又特别小（12KB、36KB 碎包）。
- **原因**：
  - 装箱算法按 `new FileInfo(file).Length` 统计体积，`.spriteatlas` 本身只有几 KB，但打包时会把它引用的所有纹理（总计几十 MB）全拉进同一个 bundle。
  - 于是图集被当成「几 KB 的小 unit」，被 best-fit 塞进容量最充裕的普通组，打包后该组瞬间膨胀。
- **分析结论**：**图集必须用真实纹理依赖体积估算，不能只看 `.spriteatlas` 文件本身。**

#### 坑 8：矫枉过正——每个 `.spriteatlas` 独立成组

- **做法**：发现坑 7 后，第一个修复方案是「每个 `.spriteatlas` 强制独立成 `Group_Atlas_XXX`」，并给每个图集用 `AssetDatabase.GetDependencies` 真实估算体积。
- **现象**：直接打出了 **104 个 bundle**。图集一多，组数就按图集文件数量膨胀，光请求握手就要爆。
- **原因**：图集组数 = 图集文件数，而不是按体积合并。**这是从「塞进普通组」矫枉过正到「完全隔离」的典型错误。**
- **正确做法**：图集仍然按体积装箱，但**只和图集合并，不和普通资源混**，组数 ≈ `ceil(总图集体积 / idealMax)`，个位数到十几个，而不是等于文件数。

#### 坑 9：装箱算法 `CurrentSize < minBytes` 判断反效果

- **代码**（有问题的版本）：
  ```csharp
  if (minCapacityGroup != null && minCapacityGroup.CurrentSize < minBytes)
  {
      minCapacityGroup.AddUnit(unit);
      continue;
  }
  // 否则创建新组
  ```
- **含义**：只有当组当前大小 `< 512KB` 时才往里塞。
- **现象**：组一旦达到 512KB 就停止接收，下一个单元只能新建组；新组从 0 开始又容易被塞到 512KB 就停，反复产生**半满组**和 **12KB / 36KB 碎包**。
- **正确做法**：改用**标准 best-fit**——优先塞进「最满且装得下」的组，把空隙填满；只有真的装不下才建新组。

#### 坑 10：category 按「目录/文件名」返回，永远无法合并

- **代码**（有问题的版本）：
  ```csharp
  var parts = path.Split('/');
  if (parts.Length >= 5) return parts[3] + "/" + parts[4];
  ```
- **对于 `Assets/Addressables/UI/Textures/foo.png`**：`parts[3] = Textures`，`parts[4] = foo.png`，返回 `Textures/foo.png`——**每个文件一个 category**。
- **后果**：`sameCategoryGroup` 永远为 null，所有资源都走全局 best-fit，分组极不稳定，同类资源被打散。
- **正确做法**：返回目录（如 `UI/Textures`），同目录资源优先聚在一起。

#### 坑 11：View 独立拆包（曾经的"最佳实践"，后来被数据推翻）

- **初衷**：`UI/View/*.prefab` 独立成 `Group_View_XXX`，让打开某个界面时只下载对应包。
- **实测数据**：13 个 View 组，体积 **6.7 KB ~ 70.5 KB**，合计约 350 KB。
- **问题**：
  - 微信小游戏 `wx.request` 最大并发约 **10**，13 个 View 触发并发限制，超出的排队。
  - 一次 HTTP 请求头部约 1~2 KB，TLS 握手 1~2 RTT。**下载 6.7 KB 的时间，握手占了大头**。
  - 合并成 1 个 350 KB 包，一次请求完成，**比 13 次请求快得多**。
- **重要澄清**：合并 ≠ 全部加载。Addressables 的 `AssetLoadMode = Requested Asset And Dependencies`（默认）**只会把被请求的 Prefab 及其依赖加载到内存**，同 bundle 里其他 Prefab 只是"躺在下载好的文件里"，不占内存。
- **最终决定**：删除 `viewPerPrefab` 功能，View prefab 与普通资源一视同仁，按目录 category 合并。

#### 坑 12：打包小程序功能「过度自动化」

- **早期做法**：反射读取 `MiniGameConfig.asset` 里的 `DST` / `webglDir` / `ProjectConf` 字段，自动改路径、自动调 `DoExport`、自动生成时间戳导出目录。
- **现象**：
  - 不同版本 WX-WASM-SDK-V2 字段结构不同，反射字段名对不上就报错。
  - 自动 DoExport 可能打包到意想不到的目录，需要一套备份/恢复逻辑。
  - 用户实际只想「打开微信转换界面」，剩下的自己点。
- **最终决定**：删掉所有反射改配置、自动 DoExport、时间戳导出目录的逻辑。**只做一件事**：
  ```csharp
  EditorApplication.ExecuteMenuItem("微信小游戏/转换小游戏");
  ```
  失败时退化为打开 `WXEditorWindow` 窗口，再失败就弹提示让用户手动点。

---

### 🌐 B. 运行时阶段（坑 13 ~ 坑 18，本次新增）

#### 坑 13：无效 Label 触发 `InvalidKeyException`，`try-catch` 抓不住

- **场景**：`PreloadManager` 按标签预下载 bundle，标签可能因版本/配置变化而失效。
- **现象**：外层 `try-catch` 完全无效，控制台仍抛出红色 `InvalidKeyException` 堆栈。
- **原因**：`DownloadDependenciesAsync` 是**异步操作**。发起调用时只是返回一个 `AsyncOperationHandle`，真正错误在后续帧由底层解析出，`try-catch` 早已执行完毕。错误通过 `handle.Status = Failed` 和 `handle.OperationException = InvalidKeyException` 传递。
- **正确做法**：
  - 用 `handle.Status` + `handle.OperationException` 判断，而非 `try-catch`。
  - 发起后先检查 `syncFailed || !handle.IsValid() || handle.Status == Failed`，提前退出。
  - 轮询循环里也判断 `handle.Status == Failed` 提前 `break`。
  - `OperationException is InvalidKeyException` 降级为 `LogWarning`，语义更清晰。
  - 可选：全局设置 `ResourceManager.ExceptionHandler` 统一收敛此类日志。

#### 坑 14：运行时资源引用字段为 null，被误判为"Addressables 加载失败"

- **场景**：`FishDetail.fishBagItemPrefab`、`BagDetail.bagItemPrefab` 在运行时为 null，报 `xxx is not assigned`。
- **初判**：怀疑 Addressables 资源加载失败 / 被过早 Release / 打包被剥离。
- **真因**：
  1. `FishDetail.fishBagItemPrefab` 是 `private` 且**没有 `[SerializeField]`**——Inspector 根本看不到该字段，无法赋值，也不会被序列化。
  2. `BagDetail.bagItemPrefab` 有 `[SerializeField]`，但 Inspector **未拖入**。
  3. 若确有外部注入，`SetFishBagItemPrefab` 里的 `if (fishBagItemPrefab == null)` 会让"首次传 null 后永远无法赋值"。
- **正确做法**：
  - 所有需要 Inspector 赋值的 `private` 字段**必须加 `[SerializeField]`**。
  - 注入方法**无条件覆盖**（仅在传入 null 时告警并忽略），避免"首帧 null 锁死"。
  - 兜底策略：`Start` 里递归查找同名子物体（`FindInChildren`），并打清晰诊断日志。
  - 修复后必须**在 Editor 中拖入并 Apply 保存 prefab**，代码无法凭空生成引用。

#### 坑 15：`Cannot instantiate objects with a parent which is persistent`

- **现象**：`BagDetail.CreateItemPrefab` 里 `Instantiate(bagItemPrefab, contentTransform)` 报此警告，新建对象跑到场景根层级，布局全乱。
- **关键误解**：曾以为是"谁偷偷加载了 BagView"，排查了 AA 加载链路、场景预放、`OpenView` 调用点，均无果。
- **真因**（两层）：
  1. **结构性根因**：`GameUIManager` 是 `DontDestroyOnLoad` 单例，它的子物体 `viewContainer` 及其下所有实例（含 BagView → BagDetail → contentTransform）**被动进入 `DontDestroyOnLoad` 场景**。而 `Instantiate` 出来的新对象默认在 active scene（`GameScene`），两边场景不一致，Unity 拒绝挂载。
  2. **触发路径**：`BagView` 已被隐藏/回池，但 `OnBagRefresh` 监听器仍在全局事件上，数据同步事件（源自 `MainGameView.BaseViewInit` 主动 `UI_RequestUpdateAllData`）无差别触发隐藏实例，在错误状态下创建 UI。
- **正确做法**（三层）：
  - **结构层**：`Instantiate` 不传 parent → `SceneManager.MoveGameObjectToScene(obj, parent.scene)` → `SetParent`。对对象池取出的对象同样做场景同步。
  - **触发层**：`OnBagRefresh` / `RefreshItems` / `UpdateBagItems` 加 `if (!gameObject.activeInHierarchy) return;` 守卫。
  - **根治层**：见坑 18，从事件系统层面消灭僵尸监听。

#### 坑 16：`scene=''`、`sceneValid=false` 的"僵尸 BagView"仍在刷新 UI

- **现象**：日志中同一 `iid` 的 BagView，`scene=''`、`sceneValid=False`、`activeInHierarchy=False`，但 `OnBagRefresh` 仍在 `t=5.3 ~ t=7.1` 持续 550+ 条刷屏。
- **伴随现象**：用户点击打开背包时，`GameUIManager.ShowExistingInstance` 又创建了**全新实例**（不同 `iid`、`scene=GameScene`），此时**新旧两个实例同时监听**同一事件。
- **真因**：
  1. 旧 BagView 在上一场景被创建，关闭回池后被 `DontDestroyOnLoad` 的 `GameUIManager` 持有，**场景卸载时未销毁**。
  2. Unity 将其 `scene` 标记为无效，`activeInHierarchy` 判为 `false`。
  3. **`CommunicateEvent.Unregister` 未能成功摘除它的监听器**（见坑 17），事件一来仍会调用。
- **正确做法**：
  - 底层：修 `CommunicateEvent.Unregister` 的匹配机制（坑 17）。
  - 架构：`GameUIManager` 在场景切换完成时主动 `ClearAllPopupPoolsOnSceneChange()`，销毁游离实例。
  - 兜底：`OnBagRefresh` 里 `activeInHierarchy` 守卫（已含在坑 15 修复中）。

#### 坑 17：`CommunicateEvent.Unregister` 对已销毁对象的委托"失效"

- **现象**：`BagView.OnDestroy` 里明明调用了 `CommunicateEvent.Unregister(EVENT_REFRESH_BAG, OnBagRefresh)`，但对象 Destroy 后事件仍被触发。
- **根因**：
  1. `CommunicateEvent` 底层用 `Delegate.Combine` / `Delegate.Remove` 维护委托链。
  2. `Delegate.Remove` 内部依赖 `Delegate.Equals` 匹配，而 **`Delegate.Equals` 对 MonoBehavior 实例方法**在对象已 `Destroy` 时行为不确定（受 Unity `== null` 重载影响），可能返回 `false` 导致移除失败。
  3. 单次 `Unregister` 仅移除一次，若同一方法被注册多次（历史代码跨 BaseViewInit 重复注册等），剩余部分仍在。
  4. **Register 使用 `+`，Unregister 使用 `-`**，若 Register 与 Unregister 之间委托链被其他事件交叉修改，`-` 可能返回原链。
- **正确做法**（根因修复，不打补丁）：
  - 在 `CommunicateEvent` 中新增 **`UnregisterAllByTarget(object target)`**：
    ```csharp
    public static void UnregisterAllByTarget(object target)
    {
        if (target == null) return;
        foreach (var evtKvp in eventTable)
        {
            var typeTable = evtKvp.Value;
            List<Type> emptyTypes = new List<Type>();
            foreach (var typeKvp in typeTable)
            {
                var original = typeKvp.Value;
                if (original == null) continue;
                var remain = new List<Delegate>();
                int removed = 0;
                foreach (var d in original.GetInvocationList())
                {
                    if (d != null && d.Target == target) removed++;
                    else remain.Add(d);
                }
                if (removed > 0)
                {
                    if (remain.Count == 0) emptyTypes.Add(typeKvp.Key);
                    else
                    {
                        Delegate combined = null;
                        foreach (var d in remain) combined = Delegate.Combine(combined, d);
                        typeTable[typeKvp.Key] = combined;
                    }
                }
            }
            foreach (var t in emptyTypes) typeTable.Remove(t);
        }
    }
    ```
  - **`d.Target == target` 用引用比较，绕开 `Delegate.Equals` 对 MonoBehavior 的不确定性**。
  - 在 `BaseView` 增加 `protected virtual void OnDestroy()`，统一调用 `CommunicateEvent.UnregisterAllByTarget(this)`。**所有 BaseView 子类的监听在 OnDestroy 时被一次性精确摘除**。
  - 子类 `OnDestroy` 改为 `protected override void OnDestroy() { base.OnDestroy(); }`，不再各自手写 `Unregister`。

#### 坑 18：`MainGameView.BaseViewInit` 主动拉数据，放大了事件系统的缺陷

- **场景**：`MainGameView`（常驻 UI）在 `BaseViewInit` 里主动 `CommunicateEvent.Modify("UI_RequestUpdateAllData")`，触发全量数据同步，进而 `Modify("Bag_RefreshItems")`。
- **表现**：本身是正确的行为（进入 GameScene 需要拉最新数据），但在坑 16、坑 17 的叠加下，成了"僵尸 BagView 刷屏"的触发器。
- **结论**：**`MainGameView` 的行为不需要改**。它是受害者，不是元凶。修好 `CommunicateEvent.UnregisterAllByTarget` + `BaseView.OnDestroy` 统一清理后，僵尸监听被摘除，主动拉数据不会再触发任何已销毁对象。
- **补充要点**：这提示了一个架构原则——**事件系统的注册/反注册必须成对，且反注册要有"按对象批量摘除"的兜底能力**。任何依赖"逐个 `Unregister` 显式调用"的设计，都会在实例生命周期复杂（回池、跨场景、Destroy 顺序不确定）时出现僵尸监听。

## 🛠️ 三、 终极解决方案

### 1. 建组：反射物理建组，绕过官方 `CreateGroup` 雷区

- **为什么**：Unity 2022 官方 `CreateGroup` 有底层模板空引用 Bug（坑 4）。
- **实现逻辑**：
  - `ScriptableObject.CreateInstance<AddressableAssetGroup>()` 在内存建组。
  - 反射设置底层真实组名 `m_GroupName`。
  - `ScriptableObject.CreateInstance` 创建 Schema（`BundledAssetGroupSchema`、`ContentUpdateGroupSchema`），存入硬盘。
  - 反射（`m_Group` 字段）把 Schema 与 Group 互相关联。
  - `AssetDatabase.CreateAsset` 把 Group 写入硬盘。
  - 反射（`m_GroupAssets` 字段）把 Group 塞入 Settings 列表，调用 `RemoveAll` 清洗可能存在的同名残留，**彻底解决 UI 显示双份组**。

### 2. 移组：单帧单次的极速异步队列

- **为什么**：`CreateOrMoveEntry` 是原子阻塞操作（坑 1、坑 3），必须让出主线程。
- **实现逻辑**：
  - 提前算好所有文件的归属，生成 `Queue<(string file, AddressableAssetGroup group)>`。
  - 注册 `EditorApplication.update`。
  - 每次 Update 只 `Dequeue` 一个任务，执行完立刻 `Repaint` 刷新进度条并结束当前帧。
  - 单次操作最多卡顿 30ms，绝不触发 `Hold on`。实测总耗时反而变短，因为让出主线程后 Unity 底层调度更顺畅。

### 3. 打标与地址：纯 IO 遍历 + 强制覆盖

- **为什么**：打标记不涉及复杂图集移组，但仍要防止大量文件阻塞。
- **实现逻辑**：`Directory.GetFiles` 纯 IO 扫描，`entry.SetAddress(assetPath, false)` **强制覆盖旧地址**，防止历史脏数据导致运行时找不到资源。

### 4. 图集体积：真实纹理依赖估算，不是 `.spriteatlas` 文件大小

- **为什么**：`.spriteatlas` 只有几 KB，但打包后 bundle 包含几十 MB 纹理（坑 7）。
- **实现逻辑**：
  ```csharp
  long GetAtlasRealSize(string atlasAssetPath)
  {
      long total = 0;
      var visited = new HashSet<string>();

      if (File.Exists(atlasAssetPath))
      {
          total += new FileInfo(atlasAssetPath).Length;
          visited.Add(atlasAssetPath);
      }

      var deps = AssetDatabase.GetDependencies(atlasAssetPath, true);
      foreach (var dep in deps)
      {
          string d = dep.Replace('\\', '/');
          if (visited.Contains(d)) continue;
          if (!d.StartsWith("Assets/")) continue;
          if (d.EndsWith(".cs") || d.EndsWith(".meta") || d.EndsWith(".asmdef")) continue;
          if (!File.Exists(d)) continue;
          total += new FileInfo(d).Length;
          visited.Add(d);
      }
      return total;
  }
  ```

### 5. 图集与纹理不重复：扫描图集引用，跳过纹理 entry

- **为什么**：如果纹理既被图集引用，又被单独标记成 Addressable entry，就会同时进入图集 bundle 和普通 bundle，**体积翻倍**。
- **实现逻辑**：
  - 先扫描所有 `.spriteatlas`，收集它们引用的纹理路径放入 `atlasTextures`。
  - 构建单元时，`atlasTextures.Contains(path)` 的纹理**直接跳过**。
  - 图集 bundle 天然包含 `.spriteatlas` + 它引用的纹理，不会重复。
  - 唯一还会重复的情况：某个 prefab **直接引用** `Assets/Textures/xxx.png` 的 Texture2D（而不是通过图集里的 sprite）。这是 prefab 层面的事，代码无法自动修。

### 6. 图集与普通资源：分开装箱，各自独立阈值

- **为什么**：图集 LZ4 压缩比约 3x，普通资源约 1.3x（prefab/json 压缩率低）。用同一套阈值会一方偏紧一方偏松。
- **实现逻辑**：`AAutoPackConfig` 里维护两套阈值。

  | 配置项 | 值 | 说明 |
  |---|---|---|
  | `minBundleKB` | 512 | 普通资源最小装箱单元 |
  | `idealMaxKB` | 2048 | 普通资源理想上限（打包后约 1.54 MB） |
  | `hardMaxKB` | 4096 | 普通资源硬上限 |
  | `atlasIdealMaxKB` | 6144 | 图集理想上限（未压缩，打包后约 2 MB） |
  | `atlasHardMaxKB` | 12288 | 图集硬上限（未压缩，打包后约 4 MB） |

- 装箱时：
  ```csharp
  bool isAtlasUnit = IsAtlasPath(unit.Key) && unit.Key.EndsWith(".spriteatlas");
  long currentIdealMax = isAtlasUnit ? atlasIdealMaxBytes : idealMaxBytes;
  long currentHardMax  = isAtlasUnit ? atlasHardMaxBytes : hardMaxBytes;
  ```

### 7. 装箱算法：best-fit + 兜底合并

- **为什么**：坑 9 的 `CurrentSize < minBytes` 判断反效果，坑 10 的 category 按文件名导致永远无法合并。
- **category 修复**：
  ```csharp
  private static string GetParentCategoryStatic(string path)
  {
      string normalized = path.Replace('\\', '/');

      // 图集：ATLAS/<目录>，同目录图集可合并
      if (normalized.EndsWith(".spriteatlas") && normalized.Contains("/Atlases/"))
      {
          var dir = Path.GetDirectoryName(normalized).Replace('\\', '/');
          if (dir.StartsWith("Assets/Addressables/"))
              dir = dir.Substring("Assets/Addressables/".Length);
          return "ATLAS/" + dir;
      }

      // 普通资源：按目录（不是"目录/文件名"！）
      var normalDir = Path.GetDirectoryName(normalized).Replace('\\', '/');
      if (normalDir.StartsWith("Assets/Addressables/"))
          normalDir = normalDir.Substring("Assets/Addressables/".Length);
      return normalDir;
  }
  ```
- **best-fit**：
  ```csharp
  // 1. 优先塞进同 category 且装得下的最满组
  var sameCategoryGroup = groups
      .Where(g => g.Category == category
          && (g.CurrentSize + unit.Value) <= currentIdealMax
          && (isAtlasUnit ? g.GroupName.StartsWith("Group_Atlas_") : !g.GroupName.StartsWith("Group_Atlas_")))
      .OrderByDescending(g => g.CurrentSize)
      .FirstOrDefault();
  if (sameCategoryGroup != null) { sameCategoryGroup.AddUnit(unit); continue; }

  // 2. 再找任意装得下的最满同类型组（图集只合并图集，普通只合并普通）
  var bestFitGroup = groups
      .Where(g => (g.CurrentSize + unit.Value) <= currentIdealMax
          && (isAtlasUnit ? g.GroupName.StartsWith("Group_Atlas_") : !g.GroupName.StartsWith("Group_Atlas_")))
      .OrderByDescending(g => g.CurrentSize)
      .FirstOrDefault();
  if (bestFitGroup != null) { bestFitGroup.AddUnit(unit); continue; }

  // 3. 装不下才创建新组
  ```
- **兜底合并**（消灭孤包）：
  ```csharp
  private int MergeSmallGroups(List<GroupPlan> groups, long minBytes, long idealMaxBytes, long atlasIdealMaxBytes)
  {
      int mergedCount = 0;
      bool merged = true;
      int guard = 0;

      while (merged && guard++ < 1000)
      {
          merged = false;
          var smallGroups = groups.Where(g => g.CurrentSize < minBytes).ToList();
          if (smallGroups.Count == 0) break;

          foreach (var small in smallGroups)
          {
              bool smallIsAtlas = small.GroupName.StartsWith("Group_Atlas_");
              long limit = smallIsAtlas ? atlasIdealMaxBytes : idealMaxBytes;

              var target = groups
                  .Where(g => g != small
                      && g.GroupName.StartsWith("Group_Atlas_") == smallIsAtlas
                      && (g.CurrentSize + small.CurrentSize) <= limit)
                  .OrderByDescending(g => g.CurrentSize)
                  .FirstOrDefault();

              if (target != null)
              {
                  foreach (var unit in small.Units) target.AddUnit(unit);
                  groups.Remove(small);
                  merged = true;
                  mergedCount++;
                  Debug.Log($"[AA] 兜底合并：{small.GroupName} ({small.CurrentSize / 1024f:F1}KB) -> {target.GroupName} (新大小 {target.CurrentSize / 1024f:F1}KB)");
                  break;
              }
          }
      }
      return mergedCount;
  }
  ```

### 8. 甜区阈值：请求少 + 流量省

**为什么是 0.5 ~ 2 MB（打包后）**：

- 微信官方建议单 AssetBundle 包体 **≤ 2 MB**。
- 微信底层 `wx.request` 最大并发约 **10 个**，包少才能避免并发排队。
- 单包 2 MB 弱网下约 1~2 秒，体验可接受。
- LZ4 压缩比：图集约 **3x**，普通资源约 **1.3x**。

**装箱阈值（≈未压缩）→ 打包后估算**：

| 类型 | 装箱 min | 装箱 ideal | 打包后健康范围（估算） |
|------|---------|-----------|---------------------|
| 普通资源 | 512 KB | 2048 KB | 0.38 ~ 1.54 MB |
| 图集 | — | 6144 KB | ~2.00 MB |
| 允许超出 | — | — | 15% 以内不警告 |

**图集硬上限**：`atlasHardMaxKB = 12288`（未压缩 12 MB ≈ 打包后 4 MB）。超过就单独成组，但一般不会触发。

### 9. 分析工具：让"哪些包有问题"一眼可见

- **`📊 分析打出来的资源`** 按钮，自动识别最新时间戳目录，逐个 bundle 打印体积。
- **分类标注**：
  - `[内置/场景组]`：`group_0_assets_all`（Built In Data）、`group_*_scenes_all`（Default Local Group 场景）。**工具管不到，需要手动改 `Bundle Mode`。**
  - `[Atlas]`：图集组，用独立阈值判断过大。
  - 无标注：普通资源组。
- **判断规则**：
  - 过小：`size < minBundleKB × 1024 / 1.3`（打包后）。
  - 过大：普通 > `idealMaxKB × 1.15`；图集 > `atlasHardMaxKB × 1024 / 3 × 1.15`。
  - 允许超出 15%，避免估算误差导致的无谓警告。
- **输出统计**：总包数、总体积、过小/正常/过大数量、图集/普通/内置分类统计。

### 10. 内置组必须手动处理

- `group_0_assets_all` = **Built In Data**（引擎管理，新版本 Addressables 可能没有 `Bundle Mode` 选项）。
- `group_*_scenes_all` = **Default Local Group 的场景**（4 MB 左右，工具改不了）。
- **手动操作**：`Window > Asset Management > Addressables > Groups` → 点 `Default Local Group` → 右侧 `Content Packing & Loading` → `Bundle Mode` 改成 `Pack Separately`。改一次永久生效。

- **不**反射改 `MiniGameConfig` 的 `DST` / `webglDir`。
- **不**自动调 `DoExport`。
- **不**自动生成时间戳导出目录。
- **只做一件事**：

### 12. 远程路径修复：去掉 `[BuildTarget]`

- **错误配置**：
  ```csharp
  public string remoteLoadPath = "https://xxx.top/aa/WebGL/[BuildTarget]";
  ```
- **正确配置**：
  ```csharp
  public string remoteLoadPath = "https://xxx.top/aa/WebGL";
  ```
- 路径里**不再手写 `WebGL` + 变量双重叠加**。多平台时另建 Profile 隔离，不要同一个 Profile 里既写死平台又保留变量。

### 13. 运行时预下载：用 `handle.Status` 代替 `try-catch`

- **为什么**：`DownloadDependenciesAsync` 的无效标签错误是异步暴露的（坑 13）。
- **实现逻辑**：
  ```csharp
  AsyncOperationHandle handle = default;
  bool syncFailed = false;
  try { handle = Addressables.DownloadDependenciesAsync(label, false); }
  catch (Exception e) { syncFailed = true; }

  if (syncFailed || !handle.IsValid()) { /* 收尾退出 */ yield break; }

  while (!handle.IsDone)
  {
      if (handle.Status == AsyncOperationStatus.Failed) break;
      /* 更新进度 */ yield return null;
  }

  if (handle.Status == AsyncOperationStatus.Succeeded) { /* 成功 */ }
  else if (handle.OperationException is InvalidKeyException) { /* 标签不存在，仅提示 */ }
  else { /* 真正的下载失败 */ }

  if (handle.IsValid()) Addressables.Release(handle);
  ```

### 14. 事件系统根因修复：`UnregisterAllByTarget` + `BaseView.OnDestroy`

- **为什么**：`Delegate.Remove` 对已销毁 MonoBehavior 不可靠（坑 17），逐个 `Unregister` 的设计在实例回池/跨场景时必然产生僵尸监听（坑 16）。
- **实现逻辑**：
  - `CommunicateEvent.UnregisterAllByTarget(object target)`：遍历 `eventTable` → 遍历每个 `typeTable` → 遍历 `GetInvocationList()` → **按 `d.Target == target` 引用比较筛除** → 重建委托链。
  - `BaseView` 增加 `protected virtual void OnDestroy()`，统一调用 `CommunicateEvent.UnregisterAllByTarget(this)`。
  - 所有 `BaseView` 子类 `OnDestroy` 改为 `protected override void OnDestroy() { base.OnDestroy(); }`，不再各自手写 `Unregister`。
  - 效果：BagView / FishBagView / MainGameView 等任意 View 被 Destroy（正常关闭、回池、场景卸载）时，其所有监听器被**精确、一次性**摘除。

### 15. PopupPool 场景切换清理

- **为什么**：`GameUIManager` 是 `DontDestroyOnLoad` 单例，PopupPool 里实例可能在场景卸载后变成 `scene=''` 的孤儿（坑 16）。
- **实现逻辑**：
  ```csharp
  public void ClearAllPopupPoolsOnSceneChange()
  {
      foreach (var kvp in _viewRuntime)
      {
          var rt = kvp.Value;
          while (rt.PopupPool.Count > 0)
          {
              var obj = rt.PopupPool.Dequeue();
              if (obj != null) Destroy(obj);
          }
          if (rt.Instance != null && !rt.Instance.scene.IsValid())
          {
              Destroy(rt.Instance);
              rt.Instance = null;
              rt.State = ViewState.NotLoaded;
          }
      }
  }
  ```
  挂接到场景加载完成事件。孤儿实例的 `OnDestroy` 触发 → 上一条的 `UnregisterAllByTarget` 自动摘除监听。

## 🛡️ 四、 核心 API 与架构总结（防坑指南）

1. **绝不使用大批量的同步 `foreach`** 进行任何 AA 操作。
2. **移组操作必须使用「单帧单次」的异步队列**。绝不能在循环中同步移组。
3. **建组操作使用反射物理建组**，并在加入 `m_GroupAssets` 前做严格的 `RemoveAll` 防重。
4. **系统组（`Built In Data`、`Default Local Group`）绝不能加入 `BundledAssetGroupSchema`**，只能在自建的组上加。**也不要尝试用工具改它们的打包模式**，去 Groups 窗口手动改。
5. **打包前必须自愈**：强制校验 `Remote.BuildPath` 路径变量非空，`AddressableAssetSettings.CleanPlayerContent()` 清缓存。
6. **图集体积必须用 `AssetDatabase.GetDependencies` 真实估算**，不能看 `.spriteatlas` 文件大小。
7. **图集引用的纹理要跳过，不作为独立 entry**，避免图集 bundle 和普通 bundle 重复打包。
8. **图集和普通资源用各自独立的阈值体系**（图集压缩比约 3x，普通约 1.3x）。
9. **装箱用 best-fit + 兜底合并**，杜绝碎包。绝不用 `CurrentSize < minBytes` 这种判断。
10. **category 必须按目录，不是「目录/文件名」**，否则同类资源永远无法合并。
11. **View 独立拆包不是万能的**：13 个小 View（< 100 KB）合并成一个包更优。只有当 View 数量很多（> 50）或单个很大（> 500 KB）时才值得独立。
12. **不要为了「自动化」而自动化打包小程序**：调起微信转换菜单、让用户自己点，更稳定。
13. **远程路径里不要双重写平台名**：手写 `WebGL` 又要 `[BuildTarget]`，会导致 `WebGL/WebGL`。
14. **运行时预下载错误用 `handle.Status` + `handle.OperationException` 判定**，`try-catch` 抓不住异步异常。
15. **需要 Inspector 赋值的 `private` 字段必须加 `[SerializeField]`**；注入方法无条件覆盖，避免首帧 null 锁死。
16. **持久化父级冲突用 `MoveGameObjectToScene` + `SetParent` 三步走**：不传 parent → 迁场景 → 挂父级。
17. **事件监听器的生命周期必须由对象生命周期管理**：`OnEnable` / `OnDisable` / `OnDestroy` 成对处理，且提供 `UnregisterAllByTarget` 兜底。
18. **常驻单例（`DontDestroyOnLoad`）的子物体池必须随场景切换清理**，否则游离实例变孤儿。

```csharp
// 6. 运行时：事件系统根因修复（按 Target 批量摘除）
public static void UnregisterAllByTarget(object target)
{
    if (target == null) return;
    foreach (var evtKvp in eventTable)
    {
        var typeTable = evtKvp.Value;
        List<Type> emptyTypes = new List<Type>();
        foreach (var typeKvp in typeTable)
        {
            var original = typeKvp.Value;
            if (original == null) continue;
            var remain = new List<Delegate>();
            int removed = 0;
            foreach (var d in original.GetInvocationList())
            {
                if (d != null && d.Target == target) removed++;
                else remain.Add(d);
            }
            if (removed > 0)
            {
                if (remain.Count == 0) emptyTypes.Add(typeKvp.Key);
                else
                {
                    Delegate combined = null;
                    foreach (var d in remain) combined = Delegate.Combine(combined, d);
                    typeTable[typeKvp.Key] = combined;
                }
            }
        }
        foreach (var t in emptyTypes) typeTable.Remove(t);
    }
}
```

## 📝 七、 后续使用者须知

拿到这个工具后，按以下流程操作：

### 第一次使用

1. 点 **【2】重置底层环境**（清掉历史脏数据）。
2. 点 **【一键打资源（含图集）】**。
3. 点 **📊 分析打出来的资源** 查看结果。

### 日常更新

- 改 Prefab / 代码 / JSON：直接点 **【一键打资源】**。
- 改图片素材：点 **【一键打资源（含图集）】**。

### 出微信小游戏包

- 点 **【一键打包】** 或 **【全自动打包】**，最后会打开微信转换界面，由你手动点击转换。

### 遇到问题时

- **显示组重复**：说明底层数据被历史操作污染，点 **【2】重置底层环境**，然后重新执行【4】和【5】。
- **包体过大**：点 **📊 分析打出来的资源**，看是 `[内置/场景组]` 还是 `[Atlas]` 还是普通组过大。
  - `[内置/场景组]` 过大：去 Groups 窗口把 `Default Local Group` 的 `Bundle Mode` 改成 `Pack Separately`。
  - `[Atlas]` 过大：把 `AAutoPackConfig.atlasIdealMaxKB` 调小（如 4096），会拆得更细。
  - 普通组过大：把 `AAutoPackConfig.idealMaxKB` 调小。
- **包数过多**：点 **⚙ 设置包大小范围**，把上限调大（如 2 MB → 3 MB），允许合并更激进。
- **图集包 404 / 加载失败**：检查 `remoteLoadPath` 是否路径重复（如 `WebGL/WebGL`），是否和服务器实际部署目录一致。
- **运行时预下载报 `InvalidKeyException`**：这是标签不存在的正常提示，不是代码 bug。检查标签配置或改为 `LogWarning`。
- **运行时 `xxx is not assigned`**：去对应 prefab 的 Inspector 拖入引用并 Apply。代码无法凭空创建引用。
- **运行时 `Cannot instantiate objects with a parent which is persistent`**：`Instantiate` 不传 parent → `MoveGameObjectToScene` → `SetParent`。
- **运行时控制台有已关闭 UI 的日志**：事件系统漏摘监听。确认 `BaseView.OnDestroy` 调用了 `CommunicateEvent.UnregisterAllByTarget(this)`，且子类 `OnDestroy` 都 `base.OnDestroy()`。

### 一定要记住

- **千万不要**手动去 Groups 窗口里拖拽大量资源，一切自动化操作，交给**单帧单次异步队列**去跑，它绝对能保护你的 CPU 和血压。
- **千万不要**用工具自动改内置组（`Built In Data` / `Default Local Group`）的打包模式。
- **千万不要**在 `remoteLoadPath` 里既写死平台名又保留 `[BuildTarget]` 变量。
- **千万不要**依赖"逐个 `Unregister` 显式调用"管理事件生命周期，**必须有 `UnregisterAllByTarget` 兜底**。
- **千万不要**把"UI 是否显示"当作"是否注册事件"的唯一判断依据，`OnEnable`/`OnDisable` + `OnDestroy` 三层都要管。

> 这份工具的核心思路：**用异步队列避免卡死、用真实体积估算避免巨包、用 best-fit + 兜底合并避免碎包、用分类分析定位问题、把手动操作留给用户；运行时用状态机代替 try-catch、用对象生命周期管理事件监听、用场景迁移解决持久化冲突。**
>
> 任何"过度自动化"都会在 SDK 升级或平台变动时变成维护负担。工具的价值不是"替用户做完所有事"，而是"把用户不想做的重复劳动做掉，把需要人工决策的事留给用户"。
