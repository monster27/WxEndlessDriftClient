# 📁 Addressables 自动化工具开发与深度排坑全记录

## 📝 一、 前言与目标
**目标**：开发一个编辑器工具（`AAutoPackTool`），实现：一键生成图集、按文件夹及包体大小智能分组、一键打 AA 标记并重置地址、无感防卡死移组、以及快捷打资源与 WebGL 包。
**核心挑战**：彻底解决在批量操作 Addressables 时，Unity 极大概率出现的 `Hold on (busy for XXXs)` 假死和底层 `NullReferenceException` 秒崩问题。

---

## 🕳️ 二、 地狱级排坑过程与错误尝试

### 坑 1：纯同步 For 循环（最初的灾难）
*   **做法**：使用 `foreach` 把几百个资源通过 `CreateOrMoveEntry` 塞入组中。
*   **现象**：瞬间假死，弹 `Hold on`，一卡就是几十秒甚至几小时。
*   **原因**：`CreateOrMoveEntry` 底层是**同步阻塞**的。每次移组，Unity 都会触发：依赖树重算（尤其是图集和 Prefab） -> 计算 Hash -> 序列化写盘 -> 刷新 UI。连续执行累加了这几百次操作的耗时，直接撑爆单帧时间。

### 坑 2：`StartAssetEditing` 批量挂起（导致死锁）
*   **做法**：用 `AssetDatabase.StartAssetEditing()` 包裹整个 For 循环，企图阻止每次移组引发的刷新。
*   **现象**：依然卡死，甚至引发更严重的底层死锁。
*   **原因**：虽然挂起了 UI，但 Addressables 移组极度依赖实时的 Asset 读取。挂起状态下拿不到最新依赖，直接内部死锁。

### 坑 3：时间片限制（伪异步）
*   **做法**：使用 `Stopwatch` 限制，每帧最多执行 20ms 就跳出，企图分帧处理。
*   **现象**：毫无作用，依然卡死。
*   **原因**：`CreateOrMoveEntry` 是**原子操作**。单次移入一个包含百张图的图集，单次执行可能就耗时 2 秒。你无法在 20ms 处中断它，它依然会把这一帧撑爆。

### 坑 4：官方 API 建组报空引用
*   **做法**：使用官方的 `settings.CreateGroup` 创建分组。
*   **现象**：抛出 `Object reference not set to an instance of an object`，但诡异的是组却成功建出来了。
*   **原因**：Unity 2022 版本中，如果底层 `AssetGroupTemplates` 文件夹或 Profile 变量丢失，官方 `CreateGroup` 在挂载 Schema 时必定报空。

### 坑 5：`Addressable content build failure (duration: 0:00:00)`
*   **现象**：打资源时瞬间秒崩，报错指向 `BuildPlayerContent` 空引用。
*   **原因**：
    1. 底层自愈代码用力过猛，给系统专属的 `Built In Data` 组强行塞入了 `BundledAssetGroupSchema`，导致底层规则冲突。
    2. 本地的 Profile 变量 `Remote.BuildPath` 没有被正确赋值，打包时读取到空路径引发崩溃。
    3. 内存中残留了同名但被销毁的 Group 引用，或者列表中存在同名组导致遍历崩溃。

## 🛠️ 三、 终极完美解决方案（为什么代码要这么写？）

### 1. 建组：使用“反射物理建组”绕过官方雷区
*   **为什么这么写**：既然官方 `CreateGroup` 有底层模板空引用的 Bug，我们直接绕过它。
*   **实现逻辑**：
    *   用 `ScriptableObject.CreateInstance<AddressableAssetGroup>()` 在内存中建组。
    *   通过反射设置底层的真实组名 `m_GroupName`。
    *   用 `ScriptableObject.CreateInstance` 创建需要的 Schema（`BundledAssetGroupSchema` 等），并存入硬盘。
    *   通过反射（`m_Group` 字段）将 Schema 与 Group 互相关联。
    *   使用 `AssetDatabase.CreateAsset` 将 Group 写入硬盘。
    *   最后通过反射（`m_GroupAssets` 字段）将 Group 塞入 Settings 列表，并调用 `RemoveAll` 暴力清洗可能存在的同名残留，**彻底解决 UI 显示双份组的 Bug**。

### 2. 移组：使用“单帧单次”的极速异步队列
*   **为什么这么写**：为了解决原子操作阻塞主线程的问题，必须把任务打碎，让出主线程。
*   **实现逻辑**：
    *   提前计算好所有文件的归属，生成一个 `Queue<(string file, AddressableAssetGroup group)>`。
    *   注册 `EditorApplication.update` 事件。
    *   每次 Update（约每秒 60 次），**只从队列 `Dequeue` 出一个任务执行，执行完立刻 `Repaint` 刷新进度条并结束当前帧**。
    *   这样哪怕单次操作耗时 30ms，它最多只卡顿 30ms，绝对触发不了 `Hold on`。而且实测总耗时反而变短了，因为让出主线程后，Unity 底层能更好地调度资源。

### 3. 打标与地址：纯 IO 遍历 + 强制覆盖
*   **为什么这么写**：打标记（Add to DefaultGroup）涉及不到复杂的图集移组，通常较快，但为了防止大量文件阻塞，依然采用分帧或原生 IO 遍历。
*   **实现逻辑**：使用 `Directory.GetFiles` 纯 IO 扫描，直接 `entry.SetAddress(assetPath, false)` **强制覆盖旧地址**，防止历史脏数据导致运行时找不到资源。

### 4. View 独立拆包逻辑
*   **为什么这么写**：`Assets/Addressables/UI/View/` 下全是界面预制体（如 `CollectionView`）。如果把它们合在一个包里，玩家打开背包时，会被迫下载商城、图鉴的包。
*   **实现逻辑**：在智能装箱算法中，遇到 `UI/View/` 下的 `.prefab`，不按文件夹合并，而是**强制以该文件为单元独立成组**，命名为 `Group_View_XXX`，确保界面按需加载。

## 🛡️ 四、 核心 API 与架构总结（防坑指南）

1. **绝不使用大批量的同步 `foreach` 循环** 进行任何 AA 操作。
2. **移组操作必须使用“单帧单次”的异步队列**。绝对不能在循环中同步移组。
3. **建组操作使用反射物理建组**，并在加入 `m_GroupAssets` 前做严格的 `RemoveAll` 防重。
4. **系统组 (`Built In Data`, `Default Local Group`) 绝不能加入 `BundledAssetGroupSchema`**，只能在自建的组上加。
5. **打包前必须自愈**：强制校验 `Remote.BuildPath` 路径变量非空，清理构建缓存。
6. **View 独立拆包**：界面预制体单独成组，保证下载粒度。
7. **图集与源图同组**：通过 `NormalizeAtlasUnit` 将图集路径与源图路径归一化，保证图集和原图算在同一个小包内，防止交叉依赖导致包体膨胀。

```csharp
// 1. 唯一正确的建组方式（避开底层 Bug + 防重复引用）
private AddressableAssetGroup CreateGroupPhysically(AddressableAssetSettings settings, string groupName)
{
    // ... 通过反射拿到 m_GroupAssets 列表
    var existingGroup = settings.FindGroup(groupName);
    if (existingGroup != null) 
    {
        // 从列表中暴力剔除重复项，保证 UI 只有一个
        groupsList?.RemoveAll(g => g == existingGroup);
        return existingGroup;
    }
    // ... 创建 Group、Schema 资产并反射写入硬盘 ...
    groupsList?.Add(group);
    return group;
}

// 2. 唯一不卡死的移组方式（单帧单次队列）
private void ProcessMoveStep()
{
    if (_taskQueue.Count == 0) {
        // 结束处理，统一 SaveAssets
        return;
    }
    // 一帧只出一个任务
    var task = _taskQueue.Dequeue();
    var entry = settings.CreateOrMoveEntry(task.guid, task.group, false, false);
    entry.SetAddress(task.path, false);
    
    _processedTasks++;
    Repaint(); // 刷新进度条
}
```
